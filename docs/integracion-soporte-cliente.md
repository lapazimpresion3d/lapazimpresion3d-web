# Comunicación de soporte entre plataformas
Fase central: migración 0012 y GET/POST administrativos /api/admin/servicios/:propuesta_id/soporte/:ticket_id/mensajes. El autor lo fija el servidor. UUID idempotente, texto 1–3000, últimos 200 mensajes, validación de pertenencia y sesión administrativa. Las intervenciones y la descripción original de las solicitudes administrativas siguen siendo privadas; no se deben devolver en una API de cliente. Guardar una respuesta no la entrega ni genera aviso externo. No hay API cliente habilitada.

## Contrato de integración propuesto, no implementado
Preferir Service Binding entre Workers si comparten cuenta. Autenticar al operador en el Worker del negocio y resolver identificador de negocio desde sesión, nunca desde parámetro no confiable. Mantener en central una vinculación explícita y revocable negocio/servicio aceptado; el central verifica esa vinculación y permiso en cada operación. No reutilizar cookie de administración ni token de Mi proyecto. No exponer secretos al navegador. Si no es posible el binding, diseñar autenticación servidor-servidor con credenciales por integración, expiración, protección de repetición y rotación. Las demos usarán exclusivamente almacenamiento ficticio aislado.
Operaciones futuras: listar solicitudes propias, crear solicitud con campos públicos separados de los internos, leer mensajes permitidos, añadir mensaje con autor cliente fijado en servidor, consultar suscripción con importes acordados y pagos registrados sin referencias privadas. Autorizar adjuntos por servicio y ticket, validar tipo y tamaño; no incluir notas internas, minutos, autorizaciones o datos de otros negocios. Estados y prioridad técnica siguen bajo control central. No hay cobro automático. Pendiente acordar identidad y transporte con el otro repositorio, implementar API cliente y pruebas negativas de aislamiento, sesión, origen, abuso y revocación.
